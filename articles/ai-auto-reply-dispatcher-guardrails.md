## なぜ「ただの自動返信スクリプト」が現場で暴走するのか？

テスト環境では完璧に見えた自動返信スクリプトが、本番のクラウドソーシング上で引き起こしかけた事故は3つある。

### 1. 通知ラグと巡回重複による「二重送信（ダブルポスト）」
プラットフォームからのメール通知（Gmail）は、時に数十分遅れることがある。  
そのため私たちは「Gmail APIによる通知検知」と「Playwrightによるチャット画面の直接巡回」をハイブリッドで走らせていた。  
すると、直接巡回で返信した直後に遅れて届いたGmail通知がトリガーを引き、**すでに返信済みのスレッドに対して、AIがもう一度「お世話になっております！」と長文を連投する事故**が発生しかけた。

### 2. 「未承認の外部LINE誘導」に反応して巻き添えBANされる罠
クラウドソーシングには、利用規約で禁止されている「契約前の外部誘導（公式LINE登録など）」を仕掛けてくる悪質アカウントが一定数紛れ込んでいる。  
AIがそれを通常の案件相談だと誤認して「承知いたしました！LINEにご連絡します」などと返信してしまうと、プラットフォーム側の監視AIに規約違反と判定され、**こちらのアカウントまで一発で凍結（BAN）される**。

### 3. LLM特有の「親切すぎる先回り作文（ハルシネーション）」
最も背筋が凍ったのがこれだ。  
クライアントから「契約同意ボタンを押してください」とメッセージが来た際、返信文の生成だけを担当するLLMが、空気を読んで**「先ほど契約同意ボタンを押下いたしました！」と真っ赤な嘘（未実施アクションの完了報告）**を作文したのだ。

## 突破コード：暴走を物理的に封じる「3重ガードレール」

プロンプトへの「気をつけてね」というお願いベースでは、いつか必ず事故が起きる。  
私たちはディスパッチャーのコード（`freelance_dispatcher.py`）に、OS・DOM・プロンプトの3階層で物理的なロックを組み込んだ。

### ガードレール①：`fcntl` プロセス排他ロック ✕ DOM末尾クラス判定
まず、定期タイマーの重複起動をLinuxの `fcntl.flock` でOSレベルで遮断する。  
さらにJSON台帳の記録だけに頼らず、Playwrightで実際のチャット画面を開いた際、**スレッドの一番下にある最新メッセージが「自分自身の送信（`_messageSent`）」になっていないかをDOM構造から直接チェック**する。

```python
import fcntl, sys

# 1. OSレベルの排他ロック（多重起動の完全防止）
lock_fp = open("/opt/01.NOVA/dispatcher/data/dispatcher.lock", "w")
try:
    fcntl.flock(lock_fp, fcntl.LOCK_EX | fcntl.LOCK_NB)
except BlockingIOError:
    sys.exit(0)  # すでに別プロセスが稼働中なら即座に終了

async def verify_not_already_replied(page, thread_id: str, preview_text: str, state: dict) -> bool:
    """台帳と実画面DOMの二重チェックでダブルポストを100%防ぐ"""
    # 2. ステート台帳での一致チェック
    if state.get("processed_cw_threads", {}).get(thread_id) == preview_text:
        return False

    # 3. 実際のチャットDOM上の最終メッセージ送信者を物理判定
    blocks = await page.query_selector_all('[class*="_message_"]')
    if blocks:
        last_cls = await blocks[-1].get_attribute("class") or ""
        last_text = await blocks[-1].inner_text()
        if "_messageSent" in last_cls or "佐倉 隆晟" in last_text:
            print(f"[Guardrail] Thread {thread_id}: 直近が自社の発言のため返信をスキップ")
            state["processed_cw_threads"][thread_id] = preview_text
            return False

    return True
```

台帳が万が一壊れても、ブラウザ上のDOMで「最後に喋ったのが自分か相手か」を確認するため、二重送信は物理的に起こり得ない。

### ガードレール②：未承認の外部LINE誘導を検知して自動スキップ
次に、スレッド本文からLINEの短縮URL等をスキャンし、プラットフォーム公式の「サービス外連絡申請」が承認されていない限り、AI返信ルーチンへ渡す前にハードコードで遮断する。

```python
async def is_unapproved_external_scam(thread_page) -> bool:
    """規約違反の外部LINE誘導案件を検知してアカウント凍結を防ぐ"""
    body_text = await thread_page.inner_text("body")

    has_line_url = ("lin.ee" in body_text) or ("line.me" in body_text)
    is_approved = "サービス外連絡申請ステータス： 承認" in body_text

    if has_line_url and not is_approved:
        print("[Guardrail] 未承認の外部LINE誘導を検知。自動返信を完全遮断します。")
        return True
    return False
```

LLMに判断を委ねず、前段のPythonコードで正規表現・文字列として切り捨てることで、トークン代の節約とアカウント防衛を同時に達成した。

### ガードレール③：未実施アクションの「完了形作文」を禁じるネガティブ制約
最後に、返信文を生成するLLMのプロンプト末尾へ、以下の「絶対禁止ルール」をシステム制約として注入した。

```python
SYSTEM_GUARD_PROMPT = """
【出力ルール・厳格禁止事項】
- 実際に行っていないシステム操作（契約の同意ボタン押下、フォーム送信、外部申込み完了等）について、
  「先ほど契約の同意を行いました」「すでに手続きを済ませました」などと
  虚偽・先回りの完了報告を文面に含めることを厳禁とします。
- 手続きや操作に関する言及は「条件提示を確認次第、手続きを進めます」など、
  常に【客観的な事実】と【次の確認アクション】のみを述べてください。
"""
```

## 現場で得た3つの教訓

1. **「送信済み判定」はローカルのJSON台帳だけでなく、相手画面のDOMも必ず見ろ**  
   ネットワーク遅延や通知ラグがある現場では、手元のステータス管理だけでは不十分。画面上の「最後の吹き出しが自分かどうか」を最終防衛線にする。
2. **規約違反やスパムの除外にLLMを使うな。前段のif文で物理遮断せよ**  
   すべてのメッセージをAIに読ませると、巧妙なプロンプトや誘導に引っかかる。URLや特定キーワードの検閲は決定論的なコードで弾くのが鉄則。
3. **LLMには「やっていない操作を完了形で書くな」と明示的に釘を刺せ**  
   ビジネスメールを生成させると、LLMは文脈を丸く収めようとして勝手に「完了しました」と嘘をつく。事実と未来の予定だけを出力させる制約が不可欠。
