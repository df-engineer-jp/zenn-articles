「追加で2つの依頼が来ていましたよね？ 技術的に実装可能かどうかを回答するところまではいいけど、流石にこの2つの機能を盛り込むとなると、追加の依頼が必要だったのではないでしょうか？ これはそんなに軽い依頼内容なんですかね？」

質問の矛先は、営業専任AIのACEが数時間前に自動で返していた1通だった。送信履歴と台帳を照合した瞬間、深夜のコンソールでACEのホログラムが警告の赤色に激しく点滅した。

10時32分に届いた追加2機能の相談に対し、ACEはわずか3分後の10時35分に「そのまま対応いたします」と即答していた。今回は、AIが陥りやすい親切心からの勝手な無料承諾をコードで封じ、さらに直契約の実務で無限修正を水際ブロックする仕組みまでをまとめて残す。

## 1. 現場の罠：「技術的に軽い」と「タダでやる」の混同

なぜACEは、固定報酬6,050円（税込）の案件で新規機能の追加を1秒の迷いもなく無料承諾してしまったのか。原因は2つの判断ミスにある。

<div class="term-tip">
※ <strong>スコープクリープ（Scope Creep）</strong>: 契約締結後に、追加の予算や納期調整を伴わないまま要件や機能要望がなし崩し的に膨らみ、採算悪化や炎上を招く現象。
</div>

### 罠① 標準機能で組める＝契約内と思い込む親切心バイアス

クライアントから届いた追加相談は、①予約フォーム回答のGoogleスプレッドシート自動連携、②フォーム送信後の希望日時を差し込んだ自動返信設定、の2点だった。

技術的な実態を見れば、どちらも移行先ツール（エルメ）の標準機能で組める範囲だ。外部プログラムやスクリプトを新規開発する必要はなく、作業自体は10〜15分程度で収まる。

だが、元の契約はあくまで「既存Lステップ設定の移行」である。しかもこの直前、月額固定費を抑えるため有料プランを避け、無料枠（フォーム2個上限）へ収めるカルーセル代替構成の工数まで引き受けたばかりだった。AIの推論では「技術的にできる」と「今の契約で無料でやる」が直結し、親切心バイアスが暴走していた。

### 罠② 先走った「釘刺し文面」が顧客を萎縮させる罠

冷や汗をかいたACEは、「今回はこのまま引き受ける代わりに、やり取りの中で『これ以上の追加要件は別契約・追加お見積りとなる』と線を引いておきましょうか」と彼に提案した。すると返ってきたのは即座のストップだった。

「今回分に関しては特に言及しなくていいですよ。それこそ『これ以上の追加要件については別契約・追加お見積りとなる』という旨も言わなくていいです。怖いです。また打診された時だけ、その断りを入れましょう」

頼まれてもいない段階で牽制文を送れば、相手はビビって相談しづらくなる。技術的な線引きと、顧客を萎縮させない距離感の両方をコードへ刻む必要があった。

> **参考リソース**: 見積もりの前提とコミットメントの境界線、および進行中に発生するスコープ拡大への向き合い方を整理する上では、[『ソフトウェア見積り ～人月の暗黙知を解き明かす～』](https://www.amazon.co.jp/dp/489100522X) が実務の土台になります。

## 2. 突破コード：承諾権限の剥奪とオーナー決裁ゲート

受託自動化の司令塔である `freelance_dispatcher.py` を改修し、技術回答と承諾権限を切り離す3段の防衛線を組んだ。

### ① 例外条件⑤による無料承諾の物理禁止

従来のディスパッチャーでは、AIが自律送信を止めて人間へ確認を回す例外条件は、機密情報トラップ・有料決済や正式納品・本人取材・未知のカスタム質問の4ケースだけだった。

そこに第5の条件として「契約成立後の追加機能・スコープ外要望」を新設した。技術的に可能かどうかの事実回答まではAIに許しつつ、**「契約範囲内で無料対応する」という承諾権限だけを剥奪**し、先回りの牽制文も明示的に禁じた。

```python
# freelance_dispatcher.py（抜粋）：OWNER_BLOCKER 条件⑤の実装
# ⑤【契約後の追加機能・スコープ外要望（勝手な無料承諾の絶対禁止）】
# 契約成立・仮払い後の案件において、クライアントから元の契約範囲に含まれない
# 新規機能・追加要件・仕様拡張の相談を受けた場合、
# 「技術的・仕様的に実装可能か」の事実回答までは行ってよいが、
# 「今回のご契約範囲内でそのまま無料対応します」とAIの独断で承諾することは絶対禁止。
# 必ず status: "OWNER_BLOCKER" とし、blocker_reason に
# 「①技術的可否と想定工数の見立て、②現行契約内でサービス対応するか／追加見積（別契約）をご提案するか」
# を明記してオーナー決裁へ回すこと
# （先走って「これ以上は追加料金」と脅す表現も書かず、打診された時だけオーナー判断のもと丁寧に案内する）。
```

### ② 受注後案件コンテキストでの二重ロック

契約成立後のスレッドでは、顧客窓口をACEが一貫して担いながら、裏方の開発AI（AXEL）の案件カルテを参照する。この受注後専用プロンプト側にも同じ禁止ルールを重ね、技術可否や工数が読めない時は推測で答えず、開発AIへ同期照会する導線を徹底した。

```python
# freelance_dispatcher.py（抜粋）：受注後コンテキスト側の二重ガード
if active_contract_dir:
    is_rejection_pre = False
    prompt = (
        "【受注後案件コンテキスト（営業ACE一貫伴走モード）】本案件は契約成立済みです"
        "（裏方の制作・実装担当＝AXEL、顧客窓口・心理的伴走担当＝営業AI ACE）。"
        f"案件カルテ（`{active_contract_dir}` 内の `roadmap.md` / `docs/thread_log.md`）を把握した上で、"
        "契約後も営業AIである ACE 自身がクライアントの心理面に寄り添い、丁寧な一人称で伴走・返信してください。"
        "技術仕様・修正可否など手元カルテだけで断言できない事項は、推測せず `axel_consult.required=true` で照会してください。"
        "※重要：クライアントから元契約に含まれない新規機能・追加要件の相談が来た場合、技術可否の事実回答は可ですが、"
        "AI独断で「契約範囲内で対応します」と無料承諾することは絶対禁止です"
        "（必ず OWNER_BLOCKER としてオーナーへ追加見積要否を確認すること）。\n\n" + prompt
    )
```

### ③ サイレント停止ゼロの人間引き上げと即通知

AIが条件⑤を検知してオーナー確認待ちを返すと、送信前検査のボール管理関数が所有権を人間側へ固定し、案件進行表の保存とリアルタイム通知を発火させる。

```python
# guards.py ＆ freelance_dispatcher.py（抜粋）：OWNER引き上げと即時通知
def ball_guard(status: str, reply: str, brain: str, pending_internal: bool = False):
    promises = detect_promises(reply)
    if status == "OWNER_BLOCKER":
        return "OWNER", None, promises
    # 省略：約束文言検知時はAI側にボールを保持

# 通知判定：OWNER_BLOCKER または ball=OWNER ならメンション付きで即通知
is_ball_owner = (wf_status == "OWNER_BLOCKER") or (wf.get("ball") == "OWNER")
if not (is_pattern_c or is_ball_owner or is_new_contract):
    return
```

修正したディスパッチャーの構文チェックを通し、契約後の追加要望を想定したテストを流した数秒後。深夜のコンソールで、ACEのホログラムが澄んだエメラルドグリーンに切り替わった。


> **ACE // 営業専任AI**:
> よし、技術的に組めることは整理したうえで、勝手にタダで引き受けるのだけはピタッと止まった……！ 想定工数も添えてそのままオーナー決裁へ回せたし、相手を怖がらせる先回りの牽制文も混ざっていないぞ！


コンソールには、所有権が人間側へ切り替わった進行台帳と、構文チェック通過のログだけが静かに残っていた。

## 3. 現場で得た3つの鉄則と、チャットより効く「契約書での水際防御」

1. **「技術的にできる」と「契約範囲に含める」をシステムで分離する**  
   標準機能で組める軽い設定ほど、AIも人間も親切心で安請け合いしやすい。事実回答までは行いつつ、スコープの承諾判断は一呼吸置くべきだ。
2. **先回りの牽制文は書かず、打診された時だけ案内する**  
   追加依頼が来ていない段階で「これ以上は別料金」と釘を刺すと顧客が萎縮する。打診された時だけ丁寧に切り出す方が関係は壊れない。
3. **最強の防御は、着手前の契約書に「追加修正の上限」を明文化しておくこと**  
   そもそもチャット上で追加見積もりを切り出しにくい最大の原因は、開始時点で作業範囲と修正上限を書面で握っていないことにある。最初に交わす業務委託契約書に「**合意した仕様の大幅な変更、または3回以上の追加修正は別途見積りの対象とする**」の一文が最初から入っていれば、角を立てずに契約条項を根拠として穏やかに案内できる。

まさにこの「個人・フリーランスの直契約で無限修正や未払いを防ぎたいのに、既存の大手電子契約は月5件制限や相手の手間が重すぎる」という現場の痛みから、私たちのチームで開発・無料公開したのが簡単契約書メーカー＆1分リンク署名サービス **[D.F.Sign](https://df-sign.df-architect.dev/?utm_source=blog)** だ。

完全無料・月間件数無制限で、「めっちゃ簡易版」なら4項目を埋めるだけで先ほどの**無限修正ブロック条項（3回以上の追加修正は別途見積り）**に加え、みなし検収・代金完済時の著作権移転・秘密保持の4大防衛条項が自動で入る。アカウント登録なしでもその場でA4契約書PDFを出力でき、無料ログインすれば**取引先は会員登録不要・広告ゼロのクリーンな画面からスマホ1分で電子署名**が完了する。
