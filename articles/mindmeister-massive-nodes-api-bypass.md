## なぜ3,000ノード超のSaaSは画面UIから死ぬのか？

MindMeister等のWebマインドマップツールは、通常数百ノード程度のツリー構造を想定して設計されている。  
これが「3,000ノード超 ✕ 数千リビジョン」に膨れ上がると、ブラウザ側で致命的な障害が起きる。

<div class="term-tip">
  <strong>Panda / Goya描画エンジンとは？</strong>: MindMeisterのフロントエンドで動くツリー構造レンダラー。ノード間の親子関係や座標計算、折りたたみ状態の同期をブラウザのメインスレッド上でリアルタイム処理する。
</div>

### 1. メインスレッド占有による「イベント発火前の死」
画面上の「過去バージョンに戻す」をクリックした際、ブラウザは即座にサーバーへ通信を送るわけではない。  
まず手元のフロントエンド側で、3,000ノードに及ぶ差分JSONのツリーをパースし、現在の画面状態との整合性を計算しようとする。

ノード数が数千件に達していると、このJavaScriptのツリー再計算だけでCPU使用率が100%に張り付き、メインスレッドが完全ロックされる。結果として、サーバーへのリクエストを送信する手前でブラウザがタイムアウト判定を下し、タブごとクラッシュしてしまうのだ。

## 第一の壁：内部API直叩きと、無情の「HTTP 500」墜落

「UIが死ぬなら、通信を横取りしてサーバーAPIを直接叩けばいい」  
私たちはブラウザの開発者ツール（F12）のNetworkタブを解析し、MindMeisterがリビジョン復元時に叩く内部エンドポイントを特定した。

```http
POST /app/api/panda_client/map_from_revision.json
Content-Type: application/json

{
  "idea_id": 4069455849,
  "revision": 4906
}
```

このAPIは、元マップ（`idea_id`）の指定リビジョン（`revision`）の状態をサーバー側で複製し、**「元データを一切傷つけずに新しい別マップとしてクローン作成する」**という理想的なエンドポイントに見えた。

これで解決した、と誰もが思った。  
しかし、コンソールからこのリクエストを実行した瞬間、返ってきたレスポンスは非情極まるものだった。

```json
HTTP/1.1 500 Internal Server Error

{
  "error": {
    "type": "internalServerError",
    "message": "Oh no, something went wrong"
  }
}
```

何度リビジョン番号を変えて叩いても、無情の `HTTP 500`。  
サーバー側で内部エラーが起き、API自体がクラッシュしていたのだ。

### 墜落の真因：740MB超のモンスターサブツリー
私たちはリビジョン履歴ログ（`mm_changes_4900_4916.json`）をダウンロードし、Pythonで詳細にパースした。  
そこで判明した事実が、私たちを戦慄させた。

クライアントが誤って削除してしまったリビジョン（Rev 4907）の差分データには、以下の恐るべきデータ量が記録されていたのだ。

- **削除されたノード数**: **1,602ノード**
- **紐付いていた画像ファイル**: **279ユニーク（合計 322.08 MB）**
- **添付ファイル**: **126ユニーク（合計 約420 MB）**
- **合計データ量**: **約740 MB 超**

マインドマップの1つの枝に、高解像度画像と重厚な添付ファイルがびっしりとぶら下がった740MB超のモンスターツリー。  
MindMeisterのサーバー側クローン処理（`map_from_revision`）は、この超大容量データを1回のリクエストで一括コピーしようとした結果、サーバー側の処理タイムアウトに引っかかり、HTTP 500を吐いて力尽きていたのだ。

API直叩きという最後の希望すら、木っ端微塵に砕け散った。

## 第二の壁：差分JSONからの手動サルベージとZIPバイナリ独自生成

「公式APIがタイムアウトで死ぬなら、差分JSONから生データを引っこ抜き、手元で完全なマップファイルを再構築するしかない」

MindMeisterには、マップをバックアップ・移行するための独自フォーマット **`.mind` ファイル** が存在する。  
`.mind` ファイルの実体は、実はただの **ZIPアーカイブ** だ。中身を展開すると、以下の構造になっている。

```text
restored_map.mind (ZIP形式)
├── map.json          ← 全ノードのツリー構造、テキスト、座標、メモ、リンク
└── images/           ← ノードに貼り付けられていた画像バイナリ群
    ├── image_001.png
    ├── image_002.jpg
    └── ...
```

私たちは、差分JSON内の `Remove` 操作ログに記録されていた `oldData`（削除される直前のノード生データ）をすべて抽出。全1,602ノードの親子関係、座標、色、メモ（note）、URLリンクを再帰的にトラバースして、完全な `map.json`（v3.0形式）をメモリ上で組み立てた。

### ブラウザ上で動くZIPエンコーダーの自作
さらに驚くべきことに、外部ライブラリ（JSZip等）を読み込めないブラウザコンソール環境で動かすため、私たちは**CRC32計算テーブルからZIPのヘッダー構造（Local File Header / Central Directory / End of Central Directory）までをゼロからJavaScriptで実装**した。

```javascript
// ブラウザコンソール上で動く超軽量ZIPバイナリ生成エンジン
function buildZip(entries) {
    const crcTable = new Uint32Array(256);
    for (let i = 0; i < 256; i++) {
        let c = i;
        for (let k = 0; k < 8; k++) c = (c & 1) ? (0xEDB88320 ^ (c >>> 1)) : (c >>> 1);
        crcTable[i] = c >>> 0;
    }
    const crc32 = (buf) => {
        let c = 0xFFFFFFFF;
        for (let i = 0; i < buf.length; i++) c = crcTable[(c ^ buf[i]) & 0xFF] ^ (c >>> 8);
        return (c ^ 0xFFFFFFFF) >>> 0;
    };
    // ... Local File Header, Central Directory, EOCDを逐次構築してUint8Arrayで結合
    return zipUint8Array;
}
```

認証済みのブラウザセッション経由で、MindMeisterのサーバーから消えた画像279枚を1枚ずつ丁寧にダウンロード。  
それらをすべてZIP内にパッキングし、無傷の `.mind` ファイルを出力することに成功した。

勝った。これで手元の `.mind` をMindMeisterの画面からインポートすれば復元完了だ――。

誰もがそう確信した。  
だが、悪夢はまだ終わっていなかった。

## 第三の壁：公式インポートUIの「200MB上限」

完成した無圧縮の `.mind` ファイルのサイズは、**312.21 MB**。

意気揚々とMindMeisterのインポート画面を開き、ファイルをドラッグ＆ドロップした瞬間、画面に無情な赤いエラーメッセージが突きつけられた。

> **「ファイルの最大サイズ 200を 312 MB 越えています」**

公式インポートUIには、**「1ファイルあたり200MB」**という絶対的な上限ガードが仕掛けられていたのだ。  
312MBのファイルは、1バイトたりとも受け付けてもらえない。

ノードデータは完璧に手元にある。画像もすべて揃っている。  
だが、サイズ制限の壁に阻まれてマップに戻すことができない。現場の空気は再び絶望に包まれた。

## 逆転の突破口：Pillow画像極限圧縮 ✕ メモ欄原本リンク埋込

ここで私たちは、エンジニアとしての総力を結集した「二段構えの最適化アーキテクチャ」を設計した。

### 1. Pillowによる視認性維持の極限画像圧縮
312MBのうち、99%を占めていたのは279枚の高解像度画像だった。  
Pythonの画像処理ライブラリ **Pillow** を用い、マインドマップ上での視認性を完全に保ちながらファイルサイズを極限まで削ぎ落とすバッチスクリプトを実行した。

- 長辺が1,100pxを超える巨大画像は、アスペクト比を維持して最大1,100pxにリサイズ。
- JPEG形式は品質82%（視覚的な劣化がほぼゼロのスイートスポット）で再エンコード。
- PNG形式は不要なメタデータをストリップして軽量化。

この最適化により、**元々322MBあった画像群は、わずか38.63MBへと激減**した。

### 2. 添付ファイルは「ノードメモ欄への直接ダウンロードリンク」へ退避
約420MBあった添付ファイル126個は、ZIP内に直接同梱することを避け、各ノードの `note`（メモ欄）の中にMindMeisterサーバー上の原本直接ダウンロードURLをMarkdown形式で自動埋め込みした（計146ノードにメモを付与）。

```markdown
<!-- 各ノードのメモ欄に自動埋め込まれたダウンロード導線 -->
📎 【添付ファイル原本】
- ファイル名: 20261111_引継ぎ資料.pdf
- ダウンロードリンク: https://www.mindmeister.com/generic_files/download/...
```

これにより、添付ファイルの実体データを失うことなく、マップファイル全体のサイズを劇的に軽量化することに成功した。

## 結び：SaaSの「ブラックボックス」をハックする力

今回の復旧劇が教えてくれたのは、現代のWeb開発における極めて重要な教訓だ。

1. **画面UIは単なる「皮」に過ぎない**: フロントエンドがフリーズしても、バックエンドとの通信やキャッシュ、差分ログの中には生データが生きている。
2. **公式APIの過信は禁物**: 大規模データ（740MB超）では、公式のエンドポイントですらタイムアウトで沈黙する。
3. **リバースエンジニアリングと独自バイナリ構築の強さ**: ファイルフォーマットの本質（`.mind` はZIPであること）を理解していれば、ブラウザ上で直接ZIPを組み立て、Pillowで圧縮して制限を突破できる。

トラブルを前にして「画面が固まったから復元できませんでした」と諦めるか。  
それとも通信とバイナリの深層へ潜り込み、泥臭くデータを救い出すか。

その境界線こそが、プロフェッショナルなエンジニアと単なるツールの使い手を分かつ唯一の差なのだ。
