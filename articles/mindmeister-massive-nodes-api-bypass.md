## なぜ3,000ノード超のSaaSは画面UIから死ぬのか？

MindMeisterなどのWebマインドマップツールは、通常数百ノード程度のツリー構造を快適に扱うよう設計されている。  
これが「数千ノード ✕ 数千リビジョン」の規模まで膨れ上がると、ブラウザ側で致命的なボトルネックが発生する。

<div class="term-tip">
  <strong>Panda / Goya描画エンジンとは？</strong>: MindMeisterのフロントエンドで動くツリー構造レンダラー。ノード間の親子関係や座標計算、折りたたみ状態の同期をブラウザのメインスレッド上でリアルタイム処理する。

### メインスレッド占有による「通信発火前の死」
画面上の「過去バージョンに戻す」をクリックした際、ブラウザは即座にサーバーへリクエストを送るわけではない。  
まず手元のフロントエンド側で、数千ノードに及ぶ差分JSONのツリーをパースし、現在の画面状態との整合性を計算しようとする。

ノード数が3,000件を超えていると、このJavaScriptのツリー再計算だけでCPU使用率が100%に張り付き、メインスレッドが完全ロックされる。結果として、サーバーへリクエストを送信する手前でブラウザがフリーズ判定を下し、タブごとクラッシュしてしまうのだ。

## 第一の壁：内部API直叩きと、無情の「HTTP 500」墜落

「UIが死ぬなら、通信を解析してサーバーAPIを直接叩けばいい」  
私たちはブラウザの開発者ツール（F12）のNetworkタブを調査し、リビジョンから別マップを生成する内部エンドポイントを特定した。

```http
POST /app/api/panda_client/map_from_revision.json
Content-Type: application/json

{
  "idea_id": 1234567890,
  "revision": 2450
}
```

このAPIは、元マップ（`idea_id`）の指定リビジョン（`revision`）の状態をサーバー側で複製し、**「元データを一切傷つけずに新しい別マップとしてクローン作成する」**という理想的なエンドポイントに見えた。

これで解決した、と誰もが思った。  
しかし、コンソールからこのリクエストを実行した瞬間、返ってきたレスポンスは非情極まるものだった。

```json
HTTP/1.1 500 Internal Server Error

{
  "error": {
    "type": "internalServerError",
    "message": "Oh no, something went wrong"
  }
}
```

何度リビジョン番号を変えて叩いても、無情の `HTTP 500`。  
フロントエンドだけでなく、バックエンドのAPI自体がサーバー内部エラーでクラッシュしていたのだ。

### 墜落の真因：700MB超のモンスターサブツリー
私たちは履歴差分APIから変更ログ（JSON）を取得し、Pythonで中身を詳細に解剖した。  
そこで浮かび上がった数値が、サーバー墜落の真因を物語っていた。

誤操作で一括削除されたリビジョンの `Remove` ログには、以下の途方もないデータ量がぶら下がっていたのである。

- **削除されたサブツリー規模**: **約1,500ノード超**
- **ノードに紐づく画像アセット**: **約280枚（合計 約320 MB）**
- **ノードに紐づく添付資料**: **100ファイル超（合計 約400 MB超）**
- **サブツリー総データ量**: **約700 MB 超**

マインドマップの巨大な枝に、高解像度スクリーンショットと重厚なドキュメント群が長年蓄積された700MB超のモンスターツリー。  
公式のクローンAPI（`map_from_revision`）は、この超大容量アセットを1回のHTTPリクエスト内で同期コピーしようとした結果、サーバー側のタイムアウト上限を超えて `HTTP 500` で力尽きていたのだ。

公式UIも公式APIも、ここで完全に全滅した。

## 第二の壁：差分JSONからの手動サルベージとZIPバイナリ独自生成

「公式APIがタイムアウトで死ぬなら、差分JSONから生データを引っこ抜き、手元でインポート用のマップファイルを再構築するしかない」

MindMeisterには、マップをバックアップ・移行するための独自フォーマット **`.mind` ファイル** が存在する。  
仕様を調査すると、`.mind` ファイルの実体は標準的な **ZIPアーカイブ** であり、展開すると以下のシンプルな構造になっていた。

```text
restored_workspace_backup.mind (ZIP形式)
├── map.json          ← 全ノードのツリー構造、テキスト、座標、メモ、リンク定義
└── images/           ← ノードに貼り付けられていた画像バイナリ群
    ├── image_001.jpg
    ├── image_002.png
    └── ...
```

私たちは、差分JSON内の `Remove` 操作ログに残されていた `oldData`（削除直前のノード生データ）を全件抽出。約1,500ノードの親子関係（`parent` 参照）、座標、色、メモ（`note`）、URLリンクを再帰的に再結合し、整合性の取れた完全な `map.json` を組み立てた。

### 外部ライブラリ不要・ブラウザ上で動くZIPエンコーダーの実装
さらに、CSP（Content Security Policy）等で外部スクリプトを読み込めないブラウザコンソール環境でも単体完結できるよう、**CRC32計算テーブルからZIPのバイナリヘッダー（Local File Header / Central Directory / End of Central Directory）までをゼロから純粋なJavaScriptで実装**した。

```javascript
// 外部依存ゼロ・ブラウザコンソール単体で動く超軽量ZIPバイナリ生成エンジン
function buildZip(entries) {
    const crcTable = new Uint32Array(256);
    for (let i = 0; i < 256; i++) {
        let c = i;
        for (let k = 0; k < 8; k++) c = (c & 1) ? (0xEDB88320 ^ (c >>> 1)) : (c >>> 1);
        crcTable[i] = c >>> 0;
    }
    const crc32 = (buf) => {
        let c = 0xFFFFFFFF;
        for (let i = 0; i < buf.length; i++) c = crcTable[(c ^ buf[i]) & 0xFF] ^ (c >>> 8);
        return (c ^ 0xFFFFFFFF) >>> 0;
    };
    // Local File Header, Central Directory, EOCDを逐次構築しUint8Arrayで結合
    return zipUint8Array;
}
```

認証セッションを通じてサーバー上に残存していた約280枚の画像バイナリを1枚ずつ保護し、再構築した `map.json` とともにZIPパッキングして `.mind` ファイルを生成した。

勝った。あとはこの `.mind` ファイルを画面からインポートすれば、新しい別マップとして完全復活する――。  
そう確信した直後、第3の壁が立ちはだかった。

## 第三の壁：公式インポートUIの「200MB上限」

生成された無圧縮 `.mind` ファイルのサイズは、**約310 MB**。

MindMeisterのインポート画面を開き、ファイルをドロップした瞬間、画面に無情な赤いエラーメッセージが表示された。

> **「ファイルの最大サイズ 200MB を超えています」**

公式インポートUIには、**「1ファイルあたり最大200MB」**という厳格なアップロード制限が設けられていたのだ。  
ノード構造も画像もすべて手元に揃っているのに、入り口のサイズ制限に阻まれてインポートできない。

## 逆転の突破口：Pillow画像極限圧縮 ✕ メモ欄リンク退避

ここで私たちは、データの欠損を一切出さずに200MBの壁を突破する「二段構えのスリム化パイプライン」を組んだ。

### 1. Pillowによる視認性維持の極限画像ダイエット
310MBの大半を占めていたのは、高解像度のまま貼り付けられた約280枚の画像ファイルだった。  
Pythonの **Pillow** を用い、マインドマップ上での文字の読解性を完全に維持したまま容量だけを削ぎ落とす一括最適化をかけた。

```python
from PIL import Image
import io

def optimize_node_image(raw_bytes: bytes) -> bytes:
    img = Image.open(io.BytesIO(raw_bytes))
    if max(img.size) > 1100:
        img.thumbnail((1100, 1100), Image.Resampling.LANCZOS)
    out = io.BytesIO()
    img.convert("RGB").save(out, format="JPEG", quality=82, optimize=True)
    return out.getvalue()
```

長辺1,100pxリサイズとJPEG品質82%（視覚劣化がほぼ判別できないスイートスポット）の再エンコードにより、**約320MBあった画像群は一気に約38MB（約88%削減）へと圧縮**された。

### 2. 大容量の添付資料は「ノードメモ欄への原本リンク」へハイブリッド格納
約400MBを超えていた100個超の添付ドキュメント群は、ローカルへ全量バックアップ保全した上で、ZIPアーカイブには直接詰め込まず、該当ノードの `note`（メモ欄）へ原本ダウンロード導線を自動埋め込みする方式を採った。

```markdown
<!-- 各ノードのメモ欄に自動注入された原本アクセス導線 -->
📎 【添付資料アーカイブ】
- ファイル名: architecture_handover_spec.pdf
- 原本リンク: https://www.mindmeister.com/generic_files/download/...
```

これにより、情報の欠落ゼロと圧倒的な軽量化を同時に成立させたのである。

## 結び：SaaSの「ブラックボックス」を解剖する力

今回の復旧劇から得られたエンジニアリング上の教訓は3つだ。

1. **画面UIは単なる「皮」に過ぎない**: フロントエンドの描画がメモリ不足で凍りついても、裏側の変更履歴ログ（JSON）には生データが生き残っている。
2. **公式APIすら大規模データでは沈黙する**: 数百MB規模のアセットが絡むと、公式のクローンAPIでさえサーバータイムアウト（HTTP 500）で墜落する。
3. **ファイルフォーマットの構造を知れば道は開ける**: 独自拡張子（`.mind`）の中身が標準的なZIP＋JSONであることを突き止めれば、手元で画像圧縮とアーカイブ再構築を行い、正面玄関（インポート機能）から安全にデータを戻すことができる。

「ボタンが固まったから復元不可能です」で終わらせるか、通信とバイナリの構造を解き明かして無傷で救い出すか。
